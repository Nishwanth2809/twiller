# Twiller staging checkpoint — Phase 6.5 Batch 3

This is a preparation runbook, not an instruction to deploy automatically. Batch 3 Circles is accepted for **local development**. Batch 4 and Phase 7 have not started. The working tree contains earlier uncommitted Phase 1–6.5 changes; review the complete diff before making any GitHub commit. Never copy local acceptance data, `.env`, Firebase service-account files, media files, or `work/` fixtures into Git.

## Isolation contract

| Layer | Staging resource | Stop if |
| --- | --- | --- |
| GitHub | `staging` branch created from this checkpoint; reviewed commits only | unrelated files, secrets, or unreviewed local artifacts are staged |
| MongoDB | Dedicated Atlas deployment or isolated staging database **`twiller_staging`**, dedicated least-privilege DB user | URI names any other database, points to production cluster unintentionally, or topology lacks transactions |
| Firebase | Separate real Firebase project and Web app; no Auth Emulator | project ID is `twill-12669` or `demo-*`, or Admin/Web project IDs differ |
| Render | Separate `twiller-staging-backend` service from `render.staging.yaml`; manual deployment | service uses the current production `render.yaml`, lacks media disk, or has a production credential |
| Vercel | Preview deployment of `staging`, root directory `twiller` | Preview lacks explicit staging Firebase config or HTTPS staging API URL |

`render.yaml`, production Firebase defaults, existing API contracts, and local acceptance settings are unchanged. The staging guards activate only when `TWILLER_DEPLOYMENT_STAGE=staging` on the backend and `NEXT_PUBLIC_TWILLER_DEPLOYMENT_STAGE=staging` in the frontend Preview build. Vercel Preview also refuses to build without the staging marker. Never set `NEXT_PUBLIC_TWILLER_LOCAL_AUTH_EMULATOR` or `FIREBASE_AUTH_EMULATOR_HOST` in staging.

## Preparation and deployment order

1. Review `git status`, `git diff`, and `git ls-files --others --exclude-standard`. The local `staging` branch is only a branch pointer until reviewed changes are committed and pushed. Stage explicit source/documentation paths rather than `git add .`; inspect the staged diff for secrets and generated files. No push occurs as part of this preparation.
2. Create a **separate** Atlas staging cluster/database and DB user. Ensure the URI explicitly ends in `/twiller_staging` before query options. Restrict network access to Render's required egress and authorized operator access; do not use a broad access list as a shortcut. Confirm replica-set primary and transaction support. Back up the staging database before indexes or any later data migration. If seeding from another environment is contemplated, use sanitized data only and perform a separate privacy review.
3. Create a separate Firebase project/Web app. Enable the intended sign-in providers, add the exact Vercel Preview host to Authorized domains, and configure password-reset/action URL domains. Generate an Admin service account **for that staging project only**. Store its JSON in Render's secret environment variable, never in Git or Vercel. Web SDK identifiers belong only in branch-scoped Vercel Preview variables.
4. Configure a real **staging** mail sender (the Blueprint expects `EMAIL_USER` and `EMAIL_PASS`); verify delivery before sign-in acceptance. An Apps Script provider can be configured instead only after reviewing its sender identity and delivery confirmation. Configure Razorpay only with **test-mode** keys on both sides if payment acceptance is needed; never perform a real charge. With no payment keys, checkout provider acceptance remains pending.
5. Run the read-only identity/Circle/Topic audits from `backend/PHASE1.md`, `backend/TOPICS.md`, and `backend/CIRCLES.md` against **staging only**. Confirm no duplicate UIDs/emails/handles, malformed conversation pairs, duplicate Circle slugs/memberships, or orphan references. Verify backup restore viability. Stop on any conflict. For a new empty staging DB, record the empty audit.
6. From a reviewed operator environment, set `TWILLER_DEPLOYMENT_STAGE=staging`, `TWILLER_STAGING_INDEXES=CREATE`, `TWILLER_STAGING_BACKUP_CONFIRMED=yes`, and the staging `MONGODB_URI`, then run `node backend/scripts/staging-indexes.mjs` from the repository root. This script checks the database name, Atlas hostname, replica-set primary, transaction support, integrity audit, and all current schema indexes including Topics and Circles; it disconnects afterward. It does **not** migrate or repair records. Do not use older generic index utilities for Batch 3. Remove the operator environment variables afterward. Never run this against production.
7. Create a **new** Render Blueprint using `render.staging.yaml` and the `staging` branch. It specifies a paid Starter service because a persistent disk is required; review cost before creating it. Supply all `sync: false` values in Render: `MONGODB_URI`, `FIREBASE_PROJECT_ID`, `FIREBASE_SERVICE_ACCOUNT`, `EMAIL_USER`, `EMAIL_PASS`, `FRONTEND_ORIGINS`, and `MEDIA_PUBLIC_BASE_URL`. `MEDIA_PUBLIC_BASE_URL` is the staging Render HTTPS service origin, without `/media`. `MEDIA_DIR=/var/data/media` is on the Blueprint's persistent disk. Automatic deploys are off. Confirm `/` health, startup index readiness, database name, and a test media upload/read. Render's disk is single-instance local storage; plan a separate media backup before relying on it.
8. In Vercel, set root directory `twiller` and Node.js version 24.x. For the **`staging` Preview branch only**, set `NEXT_PUBLIC_TWILLER_DEPLOYMENT_STAGE=staging`, `NEXT_PUBLIC_BACKEND_URL` to the staging Render HTTPS origin, and `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, `NEXT_PUBLIC_FIREBASE_PROJECT_ID`, `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`, `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`, `NEXT_PUBLIC_FIREBASE_APP_ID` from the staging Web app. Enable Vercel's automatically exposed system variables so the Preview environment marker is available. Optionally set `NEXT_PUBLIC_RAZORPAY_KEY_ID` only to a Razorpay test-mode key paired with the backend test credentials. Do not add Admin credentials to Vercel. If Vercel's Preview variables are shared by other branches, use branch-specific overrides or a separate Vercel project so they cannot point to the wrong environment.
9. After the Preview URL is known, set `FRONTEND_ORIGINS` on Render to its **exact** HTTPS origin (or an explicit comma-separated list of approved Preview origins), and add that host to Firebase Authorized domains. Redeploy the staging backend if the origin changed. Test `OPTIONS`/authenticated browser calls from the actual Preview origin, uploads and media reads, account creation, login, OTP/email, refresh, logout, Topic/Circle feeds and membership, and wrong-user denials. Confirm browser network traffic reaches only staging endpoints. Do not reuse local test credentials or records.
10. Explicitly test Google redirect on the actual Vercel Preview domain. Firebase documents browser third-party storage restrictions for `signInWithRedirect` on non-Firebase hosting; Authorized domains alone may not be sufficient. If it fails, hold staging acceptance and implement one of Firebase's supported redirect mitigations in a separately reviewed auth change. Do not switch to a production Firebase project to work around it.

## Rollback and stop gates

Before any index or data migration, take an Atlas staging snapshot/export of **users, tweets, subscriptions, conversations, messages, notifications, topics, topicfollows, circles, circlememberships, medias, loginsessions, challenges, and throttles** (check actual collection names in Atlas), and record a successful restore drill into a **different disposable database**. Back up Render's staging media disk separately. Index creation is additive, but restoring a snapshot or dropping an index still requires a reviewed plan; do not silently roll back a schema change. If a migration fails, stop the backend, preserve logs, restore the snapshot into a fresh staging database, verify counts/indexes and sample reads, then repoint only the staging service. Revert staging frontend/backend to the previous reviewed commit together if contracts diverge. Never point staging at the production database or service.

Stop deployment on: unexpected URI/project ID; failed backup or restore drill; audit conflicts; missing replica-set transaction support; index creation/readiness failure; wrong CORS origin; missing confirmed mail; failed identity/authorization checks; media 404 after upload; Preview using a production Firebase project/API; or a Google redirect failure without an approved mitigation. Provider test payments and real email delivery require separate manual acceptance before treating staging as release-ready.

## Local verification without provider access

From `backend`, run `node --test tests/staging.test.js` and the relevant existing tests. From `twiller`, run `npx tsc --noEmit`, targeted ESLint, then `npm run build` with **non-secret staging-shaped test values** and an HTTPS test API origin; this checks configuration only and does not call providers. A successful local build is not evidence that Atlas, Firebase, Render, Vercel, SMTP, or Razorpay are configured or accepted.
