# Twiller staging checkpoint — Phase 6.5 Batch 3

This is a preparation runbook, not an instruction to deploy automatically. Batch 3 Circles is accepted for **local development**. Batch 4 and Phase 7 have not started. The working tree contains earlier uncommitted Phase 1–6.5 changes; review the complete diff before making any GitHub commit. Never copy local acceptance data, `.env`, Firebase service-account files, media files, or `work/` fixtures into Git.

## Isolation contract

| Layer | Staging resource | Stop if |
| --- | --- | --- |
| GitHub | `staging` branch created from this checkpoint; reviewed commits only | unrelated files, secrets, or unreviewed local artifacts are staged |
| MongoDB | Dedicated Atlas deployment or isolated staging database **`twiller_staging`**, dedicated least-privilege DB user | URI names any other database, points to production cluster unintentionally, or topology lacks transactions |
| Firebase | Real Firebase project and Web app; an existing real project requires explicit backend and Preview opt-in; no Auth Emulator | `demo-*`, mismatched Admin/Web project IDs, or existing-project reuse without both opt-ins |
| Render | Separate `twiller-staging-backend` service from `render.staging.yaml`; manual deployment | service uses the current production `render.yaml`, lacks media disk, or has a production credential |
| Vercel | Preview deployment of `staging`, root directory `twiller` | Preview lacks explicit staging Firebase config or HTTPS staging API URL |

`render.yaml`, production Firebase defaults, existing API contracts, and local acceptance settings are unchanged. The staging guards activate only when `TWILLER_DEPLOYMENT_STAGE=staging` on the backend and `NEXT_PUBLIC_TWILLER_DEPLOYMENT_STAGE=staging` in the frontend Preview build. Vercel Preview also refuses to build without the staging marker. Never set `NEXT_PUBLIC_TWILLER_LOCAL_AUTH_EMULATOR` or `FIREBASE_AUTH_EMULATOR_HOST` in staging.

## Render Free staging mail over HTTPS

The standalone Google Apps Script source is [`docs/apps-script-mailer.gs`](docs/apps-script-mailer.gs). It accepts a bounded JSON `POST` containing a server-only secret and `{to,subject,html}`, checks the secret against Script Properties, and calls `MailApp.sendEmail` as the account executing the web app. It returns JSON `{ "success": true }` only after MailApp returns; this is provider acceptance, not proof of inbox arrival. The backend follows Content Service's response redirect, requires an HTTP success and this exact boolean acknowledgement, and retains SMTP fallback where SMTP is available. The app never sends credentials or the secret to Vercel.

Manual Google setup; the secret must not be pasted into source or a public page:

1. Use a dedicated staging Google sender account. Create a standalone project at script.google.com, paste the reviewed `docs/apps-script-mailer.gs` source, and save it. Limit project editors to trusted operators. The source contains no secret.
2. Generate one unique, random secret of at least 32 characters. Under **Project Settings → Script Properties**, add `APPS_SCRIPT_SECRET` with that value. Keep it out of source, links, screenshots, logs, and tickets.
3. Run the script's authorization flow as the sender account so MailApp's send-mail scope is approved. Check that the sender account has sufficient daily recipient quota.
4. Choose **Deploy → New deployment → Web app**. Set **Execute as: Me** (the dedicated sender). Set access so the Render server can make an unauthenticated HTTPS request (typically **Anyone**); the secret in the POST body is the authorization control. Deploy and copy the HTTPS URL ending in `/exec`, not the editor-only `/dev` URL. Do not add a `doGet` mail action.
5. In the **Render staging backend** environment only, set `APPS_SCRIPT_URL` to that `/exec` URL and `APPS_SCRIPT_SECRET` to the same value stored in Script Properties. Remove unused `RESEND_API_KEY` and `MAIL_FROM`; this transport does not use them. Never set `NEXT_PUBLIC_APPS_SCRIPT_SECRET` or any equivalent Vercel/browser variable. Deploy the reviewed backend and confirm startup says `Mail: HTTPS Apps Script configured (delivery unverified)`.
6. With an approved existing disposable account, request one login code, inspect only sanitized Render/provider status, and confirm actual inbox receipt privately. Then test correct, wrong, reused, expired, and resent codes; password-reset delivery and the Firebase hosted reset flow; and a controlled provider failure. Do not log or share codes or reset links. Failure must retain the existing safe client error and must not verify a session or change a password.

`EMAIL_USER` and `EMAIL_PASS` are optional when `APPS_SCRIPT_URL` plus `APPS_SCRIPT_SECRET` are configured. After HTTPS mail is accepted, remove **both** SMTP variables from the Free staging service if no usable SMTP fallback exists. Invoice mail no longer constructs `From` from `EMAIL_USER`; SMTP environments still set a server-controlled explicit sender. Removing only one SMTP variable fails configuration validation. The startup wording reports configuration only, never deliverability. If Apps Script times out after sending, a working SMTP fallback could send a duplicate message; it never grants session access or changes a password by itself. Google Apps Script mail quotas and Free-service ephemeral media remain separate staging acceptance concerns.

## Rollback and stop gates

Before any index or data migration, take an Atlas staging snapshot/export of **users, tweets, subscriptions, conversations, messages, notifications, topics, topicfollows, circles, circlememberships, medias, loginsessions, challenges, and throttles** (check actual collection names in Atlas), and record a successful restore drill into a **different disposable database**. Back up Render's staging media disk separately. Index creation is additive, but restoring a snapshot or dropping an index still requires a reviewed plan; do not silently roll back a schema change. If a migration fails, stop the backend, preserve logs, restore the snapshot into a fresh staging database, verify counts/indexes and sample reads, then repoint only the staging service. Revert staging frontend/backend to the previous reviewed commit together if contracts diverge. Never point staging at the production database or service.

Stop deployment on: unexpected URI/project ID; existing Firebase project reuse without both explicit staging opt-ins; any emulator or `demo-*` project; failed backup or restore drill; audit conflicts; missing replica-set transaction support; index creation/readiness failure; wrong CORS origin; missing confirmed mail; failed identity/authorization checks; media 404 after upload; or a Google redirect failure without an approved mitigation. Provider test payments and real email delivery require separate manual acceptance before treating staging as release-ready.

## Local verification without provider access

From `backend`, run `node --test tests/staging.test.js` and the relevant existing tests. From `twiller`, run `npx tsc --noEmit`, targeted ESLint, then `npm run build` with **non-secret staging-shaped test values** and an HTTPS test API origin; this checks configuration only and does not call providers. A successful local build is not evidence that Atlas, Firebase, Render, Vercel, SMTP, or Razorpay are configured or accepted.
